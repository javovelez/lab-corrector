# 07 — Uso de IA

El framework usa Claude en dos lugares: para auto-generar la
**rúbrica** de un lab y para producir **borradores de observación**
durante la corrección. Las dos cosas usan `claude-agent-sdk`,
que ejecuta sobre la sesión local de Claude Code del docente —
**sin API key**, sin HTTP propio, sin tracking de costos del lado de
la materia.

Este documento explica el SDK, el system prompt de cada uso, el
formato del prompt, el batch por fila, el contexto adicional que se
pasa para análisis y los modos de fallo.

## El SDK: `claude-agent-sdk`

Wrapper Python sobre la sesión local de Claude Code (>=0.1.64). Lo
relevante para nosotros:

```python
from claude_agent_sdk import (
    AssistantMessage, ClaudeAgentOptions, ClaudeSDKError,
    TextBlock, query,
)

options = ClaudeAgentOptions(
    system_prompt=SYSTEM_PROMPT,
    tools=[],                    # sin herramientas
    setting_sources=[],          # ignorar settings del proyecto
    permission_mode="default",
    max_turns=1,                 # one-shot
)
parts = []
async for msg in query(prompt=prompt, options=options):
    if isinstance(msg, AssistantMessage):
        for block in msg.content:
            if isinstance(block, TextBlock):
                parts.append(block.text)
text = "".join(parts).strip()
```

Decisiones de configuración:

- **`tools=[]`** — Claude no puede ejecutar bash, leer archivos ni
  buscar en la web. Solo prompt → texto.
- **`setting_sources=[]`** — ignora `CLAUDE.md` y configuración del
  agente. Esto es importante: la app no quiere que el `CLAUDE.md` de
  la materia influencie el output (eso podría hacer que Claude entre
  en modo "coautor" y empiece a hacer ediciones).
- **`max_turns=1`** — un solo turno, sin idas y vueltas. Si la
  respuesta es mala, se regenera desde la app.
- **`permission_mode="default"`** — irrelevante por `tools=[]`.

Las funciones `_run_query` (en `app/ai.py`) y `_ask_claude_rubric`
(en `app/rubric_gen.py`) son async; el wrapper público
(`generate_draft`, `generate_rubrica`) las corre con `asyncio.run`
para presentarlas como síncronas a la app.

## Uso 1 — Generación de rúbrica

Detalle completo en [03-rubricas.md](03-rubricas.md). Resumen:

- **Una llamada por ítem corregible** (no por ejercicio). Para Lab 3b
  son 15 llamadas (~1-2 min).
- System prompt en `app/rubric_gen.py::SYSTEM_PROMPT_RUBRIC`: pide
  JSON estricto con `expected` (1-3 oraciones, refiriéndose a
  funciones y variables reales de la solución oficial) y
  `common_errors` (3-6 ítems, los críticos con prefijo `"CRÍTICO: "`).
- **Prompts diferentes por kind**:
  - `code` → enunciado + código de la solución.
  - `analysis` → enunciado + pregunta + respuesta oficial + códigos
    del mismo ejercicio en la solución (contexto).
- **Modo de fallo**: si la SDK lanza `ClaudeSDKError` o el JSON sale
  mal formado, el item queda con un `expected` y `common_errors`
  marcados explícitamente como "(generación automática falló)" para
  que el docente lo edite a mano. La rúbrica se completa igual.

## Uso 2 — Borradores de observación

Vive en [`app/ai.py`](../app/ai.py). Dos modos:

### Modo A — Borrador individual

Disparado desde la vista corrección con el botón "Generar borrador
IA" (o "Regenerar"). Funciones relevantes:

- `build_prompt(...)` arma el prompt para una sola entrega.
- `generate_draft(prompt) -> str` ejecuta la query y devuelve el
  texto.

El prompt incluye:

```
Ejercicio: <título>
Corrigiendo: código | respuesta de análisis

ENUNCIADO
=========
<enunciado del ejercicio o pregunta del análisis>

QUÉ SE ESPERA
=============
<rubric.expected>

ERRORES FRECUENTES A TENER EN CUENTA
====================================
- <rubric.common_errors[0]>
- ...

SOLUCIÓN OFICIAL
================
<código o respuesta oficial>

ENTREGA DEL GRUPO
=================
<lo que escribió el alumno>

OUTPUTS DE TEXTO DE LA ENTREGA          ← solo para items code
================================
<stdout, errors — sin imágenes>

CÓDIGO DEL EJERCICIO — SOLUCIÓN OFICIAL (contexto)   ← solo para análisis
==================================================
<código del mismo ejercicio en la solución oficial>

CÓDIGO DEL EJERCICIO — ENTREGA DEL GRUPO (contexto)  ← solo para análisis
==================================================
<código del alumno en el mismo ejercicio>

OUTPUTS DE TEXTO DEL CÓDIGO DEL GRUPO (contexto)     ← solo para análisis
================================================
<stdout/errors del código del alumno>

<scope: instrucciones específicas para code o análisis>
Redactá el borrador. Si no hay nada que señalar, respondé solo: OK
```

### Modo B — Batch por fila

Disparado desde la matriz con el botón "IA" de cada fila. Genera
borradores para todos los grupos pendientes de ese ítem en **una sola
llamada** a Claude. Funciones:

- `build_batch_prompt(...)` arma un prompt con el contexto del
  ejercicio una sola vez y N entregas etiquetadas por `grupo_id`.
- `generate_batch_drafts(prompt, expected_keys) -> dict[grupo_id, str]`
  ejecuta la query, parsea JSON y devuelve un mapa.

El prompt:

```
Ejercicio: <título>
Corrigiendo: código | respuesta de análisis de N grupos en una sola pasada.

EVALUÁ CADA ENTREGA DE FORMA INDEPENDIENTE contra la rúbrica.
No compares las entregas entre sí: ...

ENUNCIADO
=========
...
QUÉ SE ESPERA
=============
...
ERRORES FRECUENTES A TENER EN CUENTA
====================================
...
SOLUCIÓN OFICIAL
================
...

[CÓDIGO DEL EJERCICIO — SOLUCIÓN OFICIAL (contexto)] ← solo análisis

ENTREGAS DE LOS GRUPOS
======================

--- grupo_01 ---
ENTREGA:
<código o respuesta>
OUTPUTS DE TEXTO:
...

--- grupo_02 ---
...

<scope>

Devolveme un único objeto JSON con una clave por grupo y como valor
el borrador (o "OK" si la entrega cumple la rúbrica). Forma exacta:
{ "grupo_01": "...", "grupo_02": "...", ... }

Reglas de salida:
- Si la entrega cumple, valor = "OK".
- Si hay algo que señalar, redactá según el system prompt.
- Devolvé SOLO el JSON. Sin texto antes ni después, sin markdown fences.
- Las claves deben ser exactamente: grupo_01, grupo_02, ...
```

#### Por qué el batch en lugar de N llamadas individuales

- **Tokens**: el contexto compartido (enunciado, expected, common
  errors, solución, contexto de código) se manda **una sola vez**.
  Para una fila con 10 grupos eso es ~5x menos tokens consumidos.
- **Latencia**: una sola roundtrip vs. 10 secuenciales.
- **Consistencia**: como Claude evalúa los 10 con el mismo contexto
  cargado, el "tono" de las observaciones es más uniforme. Esto
  aparece en el prompt explícitamente (la cláusula "EVALUÁ CADA
  ENTREGA DE FORMA INDEPENDIENTE") para evitar que Claude calibre el
  listón en base al promedio del grupo en vez de en base a la
  rúbrica.

#### Parser de salida

`_extract_json_object(raw)` tolera:

- Markdown fences (```` ```json ... ``` ````).
- Texto antes o después del JSON (recorta entre primera `{` y
  última `}`).
- Espacios y newlines extra.

Si Claude se saltea un grupo en el JSON, su clave queda fuera del
dict de salida — el caller (`_run_batch_for_item` en `main.py`)
muestra un toast con la lista de grupos faltantes y persiste solo
los que vinieron. El docente puede reintentar el batch (sigue
saltando los ya validados) o entrar a esos grupos uno por uno.

#### Cuándo no usar el batch

- **Cuando la fila tiene 1-2 grupos pendientes**: la diferencia de
  tokens no compensa la complejidad. La app igual deja el botón
  "IA" disponible — cae al batch con N pequeño y funciona igual.
- **Cuando ya validaste la mayoría**: el batch saltea los validados,
  así que en este caso es lo mismo.

## System prompt para borradores

`app/ai.py::SYSTEM_PROMPT`. Lo importante:

- **Plural por defecto**: la entrega es de un grupo, no de una
  persona. Reglas: "ustedes", "no construyeron", "les falta",
  "fíjense". Nunca "no construiste", "te falta".
- **Español rioplatense con voseo**.
- **Sin emoticones, sin fórmulas de cortesía**.
- **Tono directo y técnico, sin felicitaciones**.
- **Solo señalar lo que esté mal**. No dar instrucciones de cómo
  arreglarlo, no sugerir "agreguen X", no "deberían usar Y". El
  docente y los alumnos se encargan de la corrección; la IA solo
  identifica qué está mal.
- **Entre 1 y 4 oraciones** habitualmente.
- **Si la entrega cumple, devolver exactamente "OK"** (sin punto, sin
  nada más). La app reconoce esa cadena y guarda el draft con marker
  `<!-- ai-ok -->` (no carga texto en el textarea, solo muestra un
  hint sugiriendo "marcá sin observaciones").

## Contexto de código en preguntas de análisis (mitigación A)

Problema previo: para un item `analysis`, el prompt original solo
incluía la pregunta + la respuesta oficial + la respuesta del alumno.
Preguntas como "¿por qué usaste X?" o "¿qué muestra la curva?"
quedaban sin contexto y los borradores eran genéricos.

Solución implementada (mitigación A en la memoria del proyecto):
cada ítem `analysis` carga `companion_code_cells` (lista de cell_ids
de código del **mismo ejercicio**) en `build_items`. Al armar el
prompt se concatenan tres bloques opcionales:

- `codigo_ctx_solucion` — código del mismo ejercicio en la solución
  oficial.
- `codigo_ctx_entrega` — código del mismo ejercicio en la entrega
  del alumno (resolviendo overrides).
- `codigo_ctx_outputs` — outputs de texto de esa celda del alumno.

Aparecen como secciones extra con encabezados marcados como
"(contexto)" — el system prompt instruye que el contexto solo se
usa para entender la pregunta, no para corregir el código.

Para items `code` no aplica: son autocontenidos contra el enunciado.

## Lo que la IA NO ve

- **Imágenes**. Por costo y por simplicidad. Las mira el docente.
  Esto significa que para preguntas como "interpretá la curva de
  loss" o "describí qué cambió en la imagen estilizada", el borrador
  IA va a ser genérico. El docente las corrige a mano.
- **Otros ejercicios del mismo notebook**. Cada ítem se corrige
  aislado. Si la entrega es internamente inconsistente (p. ej. uso de
  una variable definida en un ejercicio anterior con valor distinto
  al de la solución), Claude no lo nota.
- **Otros grupos**. En el modo individual, la IA ve un solo grupo;
  en el batch, ve N pero con instrucción explícita de no compararlos.

## Decisiones explícitas

- **Sin Vision API** — descartado por costo y por alcance actual.
- **Sin "corregir todo con IA" automático** — descartado por ahora.
  Requiere un 4to estado de feedback (`ia-draft` no revisado) para
  no contaminar el txt final. Si se retoma, implica cambios en
  `state.py`, `export.py` y la matriz.
- **Sin re-uso de borradores entre items**. Cada ítem se trata por
  separado.

Más detalle en [12-decisiones-y-roadmap.md](12-decisiones-y-roadmap.md).

## Persistencia de drafts

Los drafts viven en `<workdir>/grupo_NN/feedback/<item_key>.draft.md`
(ver [09-formatos-archivo.md](09-formatos-archivo.md)). Estados:

- **No existe** → no se generó borrador todavía.
- **Texto** → borrador real, se muestra en el textarea readonly y se
  puede trasladar a la observación.
- **`<!-- ai-ok -->`** → la IA cree que la entrega cumple la rúbrica.
  La app muestra un hint y deja el textarea vacío.

El draft **nunca** va al `grupo_NN.txt` final. Solo el feedback
validado (`feedback/<item_key>.md`) se exporta.

## Modos de fallo

- **`ClaudeSDKError`** — la sesión local del SDK no respondió. Toast
  rojo con el mensaje. La app sigue. Se puede reintentar.
- **`ValueError` en el batch** — el JSON no parsea. Toast rojo. La
  app sigue.
- **Grupo sin clave en el JSON** — toast amarillo con la lista de
  grupos faltantes. Los que sí vinieron se guardan.
- **Borrador vacío o muy corto** — la app guarda lo que vino. El
  docente decide si vale la pena (típicamente, regenerar).
